# Duress Security App

تطبيق أمان وDuress لنظام Android، يجمع بين واجهة آلة حاسبة عادية في الواجهة الأولى، بوابة حماية PIN، التخزين الآمن، قفل التطبيقات، وتكاملات Android الأصلية.

> **الحالة الحالية:** المشروع قيد التطوير والتحقق المستمر عبر GitHub Actions. لا يُعتبر أي APK إصدارًا نهائيًا إلا بعد نجاح الاختبارات، TypeScript، بناء Android، وفحص الـAPK النهائي.

## الوظائف الرئيسية

### أوضاع PIN

- `0000` — الدخول العادي / Master access.
- `7777` — وضع الطوارئ: يمسح بيانات التطبيق التي يملكها التطبيق فقط، ولا ينفذ Factory Reset للهاتف.
- `5555` — Extended Lock لمدة 30 يومًا، مع حفظ الحالة ومحاولة استعادتها بعد إعادة التشغيل ضمن ما تسمح به قيود Android.
- `4444` — Fake Calculator Mode بواجهة آلة حاسبة عادية.
- PIN غير صحيح — رفض المحاولة وتطبيق حماية من المحاولات المتكررة.

> رموز الـPIN المذكورة أعلاه هي رموز افتراضية للمشروع وليست بديلًا عن PIN نظام Android. يجب التعامل معها كجزء من بيئة الاختبار/التطوير وعدم اعتبارها أسرارًا مضمونة لمجرد وجودها في التطبيق.

## واجهة الآلة الحاسبة

- تظهر الآلة الحاسبة كواجهة عادية عند فتح التطبيق.
- تصميم متجاوب وملء الشاشة على الشاشات الكبيرة، بدل حصر الآلة في عرض صغير.
- زر `0` عريض ومتمركز بصريًا.
- لا يوجد زر حماية ظاهر داخل واجهة الآلة الحاسبة.
- دخول المالك المخفي يستخدم تسلسلًا دقيقًا منفصلًا عن الحساب العادي:

  **`%` → `×` → `%` → `=`**

- عند إدخال التسلسل الصحيح من الحالة المناسبة، تفتح بوابة الحماية مباشرة لطلب PIN، بدون زر وسيط وبدون نافذة مؤقتة ظاهرة.
- التسلسل لا يعتمد على `eval` أو على اتصال شبكي.

## الأيقونة والهوية البصرية

- أيقونة Android أصبحت VectorDrawable موثوقة يتم توليدها من مصدر Android النهائي أثناء إعداد البناء.
- تم إزالة الاعتماد على أيقونة Android Robot أو الأيقونة القديمة الخاصة بالآلة الحاسبة.
- اسم التطبيق الظاهر للمستخدم هو **الآلة الحاسبة** في الواجهة الحالية لإبقاء العرض الأول طبيعيًا.
- هوية الحزمة الأمنية الداخلية تبقى `com.duresssecurity.app` ولا تتغير بسبب العلامة الظاهرية للحاسبة.

## حماية جلسة التطبيق

- يتم قفل جلسة التطبيق عند انتقال WebView/Activity إلى الخلفية عندما تكون الجلسة مفتوحة.
- يوجد مسار native إضافي عند `Activity.onStop()` لإبلاغ طبقة الواجهة بضرورة إعادة القفل.
- عند بدء العملية من جديد، تعتمد استعادة الحالة على الحالة الأمنية المحفوظة بدل افتراض أن الجلسة ما زالت مفتوحة.
- عند تعذر الوصول إلى التخزين الآمن في مسارات الحماية، يعمل التطبيق بأسلوب **fail-closed** بدل تعطيل الحماية تلقائيًا.

## قفل التطبيقات ومحاولات PIN

- تكامل Accessibility App Lock يمكنه عرض بوابة حماية قبل الوصول إلى التطبيقات التي تم تحديدها ضمن السياسة.
- عداد محاولات App Lock محفوظ لكل حزمة تطبيق ولا يتم تصفيره لمجرد إعادة عرض بوابة الحماية.
- حالة الحظر المؤقت تُحفظ مع عدد المحاولات.
- فشل قراءة أو فك تشفير حالة المحاولات لا يتحول إلى سماح؛ المسار الآمن هو الرفض حتى تتعافى حالة التخزين.

## الأمان والتخزين

- Android Keystore لتخزين مفاتيح التشفير.
- AES-GCM للبيانات الحساسة.
- Secure Storage بدل الاعتماد على تخزين PINات حساسة كنص عادي داخل واجهة التطبيق.
- حماية من العبث ببيانات الـvault ومحاولات PIN المتكررة.
- Fail-closed عند أخطاء التخزين في مسارات الحماية.
- Vault يعتمد على PBKDF2 وAES-GCM ولا يحتوي على plaintext fallback للبيانات المشفرة.
- emergency reset محصور ببيانات التطبيق المملوكة له ولا يستدعي Android factory reset.

## Android Native

يتضمن المشروع تكاملات لـ:

- `DevicePolicyManager.lockNow()` عبر Device Admin عندما تكون الصلاحية متاحة.
- `BiometricPrompt`.
- Secure Storage باستخدام Android Keystore.
- Permission handling.
- Launchable Apps.
- Accessibility App Lock.
- Device Owner / Kiosk عند توفر provisioning الرسمي.
- سياسات منع إزالة التطبيق عندما تسمح صلاحيات Device Owner بذلك.
- Boot/restart handling ضمن قيود Android الحديثة.

### Kotlin / Android build

- يتم تضمين `MainActivity.kt` وباقي Native security classes ضمن ناتج Android بشكل صريح.
- إعداد Java/Kotlin موحد على JVM 21 في مسار البناء الحالي.
- يستخدم المشروع Kotlin Android plugin مع إعداد متوافق مع Gradle/AGP المستخدمين في بيئة البناء.
- إعداد Android النهائي يزيل صلاحيات `INTERNET` و`ACCESS_NETWORK_STATE` من الـmanifest النهائي لأن التطبيق مصمم ليعمل دون شبكة.

## Device Owner / Kiosk

هذه الوظائف مخصصة للأجهزة المخصصة أو أجهزة الاختبار التي يمكن Provisioning لها رسميًا كـDevice Owner.

التطبيق العادي لا يستطيع أن يجعل نفسه Device Owner تلقائيًا، ولا يستطيع استبدال Android Keyguard الحقيقي.

يجب توفير مسار خروج واسترداد واضح قبل تفعيل Kiosk على جهاز مخصص.

## القيود المعروفة في Android

- التطبيق **لا يستبدل Android Keyguard** ولا يستطيع أن يصبح شاشة القفل النظامية لمجرد كونه تطبيقًا عاديًا.
- `BiometricPrompt` القياسي لا يكشف للتطبيق هوية الإصبع/البصمة التي استخدمها المستخدم.
- PIN التطبيق لا يستطيع قراءة أو تغيير PIN النظام.
- `5555` لا يمنع إقلاع الهاتف ولا يستبدل حماية Android عند الإقلاع.
- `7777` لا ينفذ Factory Reset؛ المسح محصور ببيانات التطبيق المملوكة له.
- التشغيل التلقائي بعد الإقلاع، تشغيل الواجهات من الخلفية، والـoverlays تخضع لقيود Android وإصدار النظام وإعدادات الجهاز.
- منع إزالة التطبيق بشكل قوي يعتمد على Device Owner/إدارة الجهاز؛ Device Admin العادي لا يجعل التطبيق غير قابل للإزالة بشكل مطلق.
- Accessibility App Lock يعتمد على صلاحية Accessibility التي يجب أن يمنحها المستخدم، ولا يمكن للتطبيق تجاوز سياسات Android أو استخدام هذه الصلاحية كآلية تخفٍ غير مشروع.

## Screenshots / التوثيق

- لا يتم فرض `FLAG_SECURE` على شاشة الآلة الحاسبة أو واجهة الحماية الحالية.
- يمكن أخذ screenshots لأغراض التوثيق والاختبار من الحاسبة وشاشات الحماية/الإعدادات.
- هذا لا يعني أن Android أو التطبيقات الأخرى ستسمح دائمًا بالتقاط screenshots في كل الحالات؛ بعض الشاشات النظامية قد تفرض قيودها الخاصة.

## Offline-first

المشروع مصمم ليعمل دون اعتماد على خادم خارجي أثناء التشغيل.

- Network guard يمنع الاتصالات إلى origins خارجية.
- لا يتم السماح بنطاقات خارجية مثل `grok.com` ضمن مسار التشغيل.
- الـAndroid manifest النهائي تتم مراجعته للتأكد من عدم وجود `INTERNET` أو `ACCESS_NETWORK_STATE`.
- أدوات التطوير وGitHub Actions تحتاج الإنترنت لتنزيل dependencies وAndroid SDK أثناء **البناء فقط**؛ هذا لا يعني أن التطبيق نفسه يحتاج اتصالًا بالشبكة أثناء التشغيل.

## الاختبارات والتحقق

اختبارات المشروع تغطي، من ضمنها:

- مسارات PIN وDuress PIN.
- Extended Lock لمدة 30 يومًا وحفظ/انتهاء الحالة.
- emergency wipe المحصور ببيانات التطبيق.
- Android Keystore وAES-GCM.
- Biometric bridge.
- Device Owner/Kiosk guards.
- Accessibility App Lock.
- retry lockout وحفظ حالة المحاولات.
- fail-closed عند أخطاء التخزين.
- vault tamper detection.
- منع Factory Reset ضمن emergency reset.
- ظهور الحاسبة كواجهة أولى.
- التسلسل السري الدقيق `%×%=` ودخوله المباشر إلى بوابة الحماية.
- تمركز زر الصفر وعدم وجود مسار حماية مرئي قديم.
- وجود Native Kotlin entrypoint في إعداد Android.
- فحوصات الـoffline manifest والـnetwork guard.

عدد الاختبارات قد يتغير مع إضافة اختبارات جديدة؛ المرجع النهائي هو نتيجة GitHub Actions للـcommit الحالي، وليس رقمًا ثابتًا محفوظًا في هذا الملف.

## التطوير والبناء

ثبّت متطلبات Node/npm وAndroid SDK الخاصة بالمشروع ثم شغّل الاختبارات قبل إجراء تعديلات.

التحقق المحلي الأساسي:

```bash
npm install
npm test
npm run typecheck
npm run apk:debug
```

وظائف Device Owner/Kiosk تحتاج جهازًا مخصصًا أو بيئة اختبار مع provisioning رسمي.

## CI / GitHub Actions

مسار Android CI يقوم بالتحقق من:

1. تثبيت dependencies.
2. اختبارات المشروع.
3. TypeScript.
4. إعداد Android وNative Kotlin.
5. بناء Debug APK.
6. فحص الـAPK والـmanifest النهائي للتأكد من عدم وجود صلاحيات الشبكة غير المطلوبة.
7. رفع APK كـartifact عند نجاح البناء.

**وجود source code أو commit أخضر في مرحلة الاختبارات وحدها لا يعني أن APK جاهز.** الإصدار القابل للتجربة يعتبر صالحًا فقط عندما تنجح جميع مراحل CI المطلوبة ويظهر artifact للـAPK.

## ملاحظات أمنية

هذا المشروع تطبيق أمان/بحث وتخرج، وليس بديلًا عن آليات أمان Android النظامية أو إدارة الأجهزة المؤسسية. يجب اختبار Device Admin وAccessibility وDevice Owner/Kiosk على أجهزة اختبار مخصصة، مع الاحتفاظ بمسار استرداد واضح وعدم استخدام الصلاحيات لتجاوز حماية النظام أو مراقبة الآخرين دون إذن.
