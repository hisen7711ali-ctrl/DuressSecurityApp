# Duress Security App

تطبيق Android أمني وتجريبي بواجهة **آلة حاسبة محلية**، وبوابة حماية PIN، وتخزين آمن، وApp Lock وتكاملات Android الأصلية.

> **الحالة:** المشروع قيد التطوير والتحقق عبر GitHub Actions. لا يُعتبر أي APK نهائيًا إلا بعد نجاح الاختبارات، TypeScript، بناء Android وفحوصات الـAPK النهائية.

## الواجهة والدخول المخفي

عند فتح التطبيق تظهر الآلة الحاسبة كواجهة أولى عادية وملء الشاشة، بدون زر حماية ظاهر.

### رمز الدخول المخفي

التسلسل الحالي والدقيق هو:

**`2 → 0 → 2 → 7 → 2 → 0 → 0 → 6 → =`**

أي أن الرمز الكامل هو:

**`20272006=`**

بعد الضغط على `=` بعد الرقم الثامن، يجب أن تنتقل الحاسبة مباشرة إلى **بوابة الحماية PIN**. لا يوجد ضغط متكرر على `=`، ولا زر وسيط، ولا اعتماد على الإنترنت.

الحاسبة نفسها حقيقية ولا تستخدم JavaScript `eval` لتنفيذ العمليات.

## PIN والحماية

| PIN | الوظيفة |
|---|---|
| `0000` | Master PIN — الدخول العادي إلى مساحة الحماية |
| `4444` | Duress / Fake Calculator Mode |
| `5555` | Extended Lock لمدة 30 يومًا |
| `7777` | Emergency wipe لبيانات التطبيق المملوكة له فقط |
| PIN آخر | رفض المحاولة مع حماية من المحاولات المتكررة |

عند إدخال **`0000`** في بوابة الحماية، يتم قبول الـPIN تلقائيًا بعد الرقم الرابع والدخول إلى التطبيق المحمي، بدون زر تأكيد إضافي.

هذه القيم افتراضية/اختبارية للمشروع وليست بديلًا عن PIN نظام Android.

### Emergency `7777`

المسح الطارئ محصور في بيانات التطبيق التي يملكها التطبيق. لا ينفذ Android Factory Reset ولا يمسح بيانات الهاتف الشخصية.

### Extended Lock `5555`

يحفظ التطبيق حالة القفل ومدة الثلاثين يومًا ضمن التخزين الأمني ويحاول استعادتها بعد إعادة التشغيل ضمن قيود Android.

- كلمة **«التطبيق قيد الصيانة»** قابلة للنقر وتفتح شاشة استرداد تحتوي على العبارة «ضع كلمة السر لإلغاء وضع الصيانة.» كما بقي مسار الاسترداد السري أعلى الشاشة.
- لوحة الرمز تُرسل المحاولة تلقائيًا بعد أربعة أرقام، وتُظهر مهلة انتظار بعد المحاولات الخاطئة.
- الاسترداد ينهي قفل الصيانة داخل التطبيق فقط؛ لا يعطّل تلقائيًا Kiosk أو سياسة منع الإزالة.
- تعرض الشاشة شريط حالة أندرويد الحقيقي، بدل رسم شريط مزيّف للساعة والإشارة والبطارية. تبقى ساعة التطبيق الكبيرة ضمن التصميم.
- بعد حفظ قفل `5555`، يحاول التطبيق قفل الهاتف عبر `DevicePolicyManager.lockNow()` **فقط** إذا كانت صلاحية Device Admin مفعّلة وكان قفل النظام الآمن مضبوطًا. إن غاب أحد الشرطين، تبقى صيانة التطبيق فعالة وتظهر رسالة توضح ما يلزم؛ لا يستطيع التطبيق إنشاء كلمة مرور النظام نيابةً عن المستخدم.

## Offline / Local App

التطبيق مصمم ليعمل **بدون اتصال إنترنت أثناء التشغيل**.

- واجهة التطبيق وملفات WebView مضمّنة محليًا داخل الـAPK.
- لا يعتمد التطبيق على موقع ويب أو خادم خارجي لعرض الشاشة الرئيسية.
- إعداد Capacitor يستخدم `dist/client` كـ`webDir` محلي.
- لا توجد سماحية تشغيلية لـ`INTERNET` أو `ACCESS_NETWORK_STATE` في الـmanifest النهائي.
- GitHub Actions وبيئة التطوير تحتاجان الإنترنت فقط أثناء البناء وتنزيل dependencies وAndroid SDK/Gradle.

> ملاحظة: الواجهة مبنية بتقنيات Web UI لكنها **معبأة محليًا داخل تطبيق Android** وليست موقعًا خارجيًا يتم تحميله من الإنترنت.

## حماية جلسة التطبيق

- عند فتح بوابة الحماية من الحاسبة يتم تعطيل استعادة الحاسبة أثناء انتقال الدخول.
- بعد نجاح Master PIN لا يفترض أن تعيد أحداث visibility/background المؤقتة المستخدم مباشرة إلى الحاسبة.
- جلسة التطبيق تُقفل عند الانتقال للخلفية وفق سياسة الحماية.
- `MainActivity.onStop()` يرسل إشارة native إضافية لإعادة القفل عند الحاجة.
- أخطاء التخزين الأمني في مسارات الحماية تعمل بأسلوب **fail-closed**.

## App Lock

عند منح Accessibility permission يمكن استخدام App Lock للتطبيقات المحددة في السياسة.

- تظهر بوابة PIN قبل الوصول إلى التطبيقات المحمية.
- شاشة القفل الأصلية تستخدم لوحة أرقام داخلية، لا لوحة مفاتيح Android؛ تحتوي على أزرار الأرقام، مفاتيح الرموز `أ` و`ي` و`ع`، حذف، وتأكيد.
- يُرسل الرمز تلقائيًا عند اكتمال أربعة محارف، ويمكن أيضًا استخدام زر التأكيد.
- الرمز الرئيسي يفتح التطبيق المستهدف مباشرةً.
- لوحة القفل الأصلية تحتوي على الأرقام والرموز نفسها `أ` و`ي` و`ع`، والحذف والتأكيد، والاهتزاز اللمسي، والإرسال التلقائي بعد أربعة محارف.
- رموز المالك المهيأة في شاشة الدخول تُمرَّر إلى دالة `submitPin` الأصلية داخل التطبيق: Duress ينتقل إلى وضع الحاسبة الوهمية، وExtended Lock يفعّل صيانة الثلاثين يومًا ويحاول قفل أندرويد، ورمز الطوارئ يمسح بيانات التطبيق المملوكة له فقط.
- عداد محاولات محفوظ لكل package. بعد خمس محاولات خاطئة، يُفرض حظر مؤقت لمدة 15 ثانية.
- إعادة عرض البوابة لا تصفّر العداد. فشل قراءة أو فك تشفير سياسة الحماية أو سجل المحاولات لا يتحول إلى fail-open.
- **الحد الحالي:** بصمة `BiometricPrompt` متاحة في بوابة التطبيق الرئيسية عند تفعيلها، لكنها لا تُعرض بعد داخل بوابة Accessibility الأصلية. هذه إضافة منفصلة مقترحة وليست مفعّلة في شاشة قفل التطبيق الخارجي.

## وضع Kiosk (تقييد الجهاز) — دليل الاستخدام الفعلي

### ما هو Kiosk في هذا المشروع؟

**Kiosk ليس رمز PIN ولا ميزة قفل تطبيق واحد.** هو محاولة تشغيل الحاسبة في وضع أندرويد المسمّى **Lock Task Mode**، والمخصص للأجهزة التي يُراد أن تبقى ضمن تطبيق واحد أو مجموعة تطبيقات معتمدة. يناسب مثلًا جهازًا مخصصًا لعرض الحاسبة فقط أو جهازًا مخصصًا لمهمة محددة.

### ماذا ينفّذ الكود الموجود حاليًا؟

عند تشغيل المفتاح من إعدادات التطبيق، يحاول الجسر الأصلي تنفيذ هذه الخطوات:

1. يتحقق أولًا من أن تطبيق الحاسبة مسجّل لدى أندرويد بصفته **Device Owner**.
2. يضيف حزمة تطبيق الحاسبة وحدها إلى قائمة التطبيقات المسموح لها بالبقاء في Lock Task Mode.
3. على Android 9/API 28 وما بعده، يضبط ميزات واجهة وضع التقييد باستخدام `LOCK_TASK_FEATURE_HOME`.
4. يطلب من النشاط الحالي بدء Lock Task Mode.
5. عند إيقاف المفتاح، يطلب إيقاف Lock Task Mode وإزالة الحاسبة من القائمة المسموح بها.

إذا رفض أندرويد الخطوة المطلوبة، يعيد الجسر نتيجة فشل ويعرض التطبيق رسالة تفيد بأن أندرويد لم يسمح بتفعيل الوضع. لذلك **ظهور المفتاح في الواجهة لا يعني أن Kiosk قد أصبح فعالًا**؛ يجب التحقق من حالة الجهاز ورسالة النتيجة.

### ما الذي يمكن أن يقيّده عند نجاح التفعيل؟

على جهاز أُعدّ رسميًا كجهاز مُدار، ومع إصدار أندرويد يدعم Lock Task Mode، يقيّد هذا الوضع الانتقال إلى التطبيقات غير المدرجة في قائمة السماح. في هذا المشروع، القائمة التي يضبطها الكود تحتوي على تطبيق الحاسبة وحده.

**انتبه إلى إعداد الواجهة الحالي:** في Android 9 وما بعده، يستدعي الكود `setLockTaskFeatures(..., LOCK_TASK_FEATURE_HOME)` ويُمرّر ميزة Home وحدها. وفق توثيق أندرويد، الميزات التي لا تُذكر في هذه القائمة تُعطّل أثناء Lock Task. لذلك لا يطلب الكود إبقاء لوحة الإشعارات، ومعلومات شريط الحالة، وشاشة التطبيقات الأخيرة، وقائمة إجراءات الطاقة، أو شاشة القفل مفعّلة. قد يصعّب هذا الوصول إلى بعض أدوات النظام، وقد لا تظهر قائمة إيقاف التشغيل عند الضغط المطوّل على زر الطاقة، بحسب إصدار النظام وتنفيذه. لهذا السبب **لا تختبر Kiosk على هاتفك الأساسي**.

**تفصيل زر الشاشة الرئيسية:** قد يظهر زر Home لأن الكود يفعّل `LOCK_TASK_FEATURE_HOME`، لكن أندرويد يوضح أن الضغط عليه لا ينقل المستخدم إلى المشغّل الافتراضي ما لم يكن المشغّل مسموحًا به في سياسة Lock Task. الكود الحالي لا يضيف المشغّل الافتراضي إلى قائمة السماح ولا يعيّن الحاسبة تطبيق Home افتراضيًا. أما الإصدارات الأقدم من Android 9 فلا يضبط الكود لها مجموعة ميزات الواجهة نفسها، وقد يختلف السلوك حسب النظام والشركة المصنّعة.

### كيف أفعّله من داخل التطبيق؟

1. استخدم **نسخة Android المثبّتة** من التطبيق؛ المعاينة في المتصفح لا تستطيع تفعيل سياسات الجهاز الأصلية.
2. افتح الحاسبة، ادخل بالطريقة المعتادة إلى مساحة الحماية، ثم افتح **الإعدادات**.
3. قبل تشغيل Kiosk، يجب أن يكون الجهاز قد أُعدّ مسبقًا بحيث يكون التطبيق **Device Owner**. لا يستطيع التطبيق منح نفسه هذه الصفة من داخل الإعدادات.
4. شغّل مفتاح **وضع الجهاز المخصّص (Kiosk)**. سيطلب التطبيق تأكيد العملية بالرمز الرئيسي وفق نافذة التأكيد الموجودة فيه.
5. راقب النتيجة: حالة إدارة الجهاز توضّح ما إذا كانت صفة Device Owner متاحة، وحالة Kiosk الفعلية تُقرأ من حالة Lock Task التي يبلغ عنها أندرويد. إذا ظهرت رسالة أن أندرويد لم يسمح بالتفعيل، فالوضع لم يُفعّل بنجاح.

### ما الفرق بين Device Admin وDevice Owner؟

هما صلاحيتان مختلفتان وليستا اسمين للشيء نفسه:

- **Device Admin (مسؤول الجهاز):** زر التفعيل الموجود في إعدادات التطبيق يطلب من أندرويد صلاحية الإدارة التقليدية. يستخدم المشروع هذه الصلاحية، عند توفرها، لطلب قفل الشاشة عبر `DevicePolicyManager.lockNow()`.
- **Device Owner (مالك الجهاز):** وضع إدارة أعلى يحتاج إلى إعداد رسمي للجهاز المُدار. يعتمد الكود عليه لتطبيق سياسة منع إزالة التطبيق وللسماح بتفعيل Kiosk. مجرد الموافقة على نافذة Device Admin لا تجعل التطبيق Device Owner ولا تكفي وحدها لتشغيل Kiosk.

تعيين Device Owner يتم عبر مسار إعداد/Provisioning مخصص لأجهزة أندرويد المُدارة، وليس بزر داخل التطبيق. قد يتطلب تجهيز الجهاز من البداية وفق تعليمات أندرويد أو مسؤول المؤسسة؛ لا تفترض أن هاتفًا شخصيًا مُعدًّا مسبقًا يمكن تحويله إلى هذه الحالة دون إعادة تهيئة أو شروط إضافية. راجع [دليل Android الرسمي لوضع Lock Task](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode) و[إرشادات الأجهزة المخصصة](https://developer.android.com/work/dpc/dedicated-devices).

#### اختبار منع الإزالة على محاكي تملكه فقط

صلاحية Device Admin العادية لا تمنع حذف التطبيق. لاختبار واجهة `setUninstallBlocked`، يلزم تهيئة **محاكي Android Studio تجريبي جديد** كـ Device Owner وفق آلية أندرويد الرسمية. لا تنفّذ هذه الخطوات على هاتفك الأساسي أو جهاز شخص آخر.

1. شغّل المحاكي وحده، وتأكد من أن `adb devices` يعرض المحاكي فقط؛ افصل أي هاتف حقيقي من USB.
2. ثبّت APK التجريبي داخل المحاكي وافتحه مرة واحدة.
3. من PowerShell أو Terminal نفّذ الأمر التالي. يجب أن يكون المحاكي غير مرتبط بحسابات أو مستخدمين آخرين، وإلا قد يرفض أندرويد التهيئة:

```powershell
adb shell dpm set-device-owner com.duresssecurity.app/com.duresssecurity.admin.AdminReceiver
```

4. افتح التطبيق وتأكد من ظهور حالة إدارة الجهاز على أنها مفعّلة. بعد ذلك اختبر مفتاح منع الإزالة من داخل التطبيق.

هذا أمر تهيئة جهاز مُدار مخصّص للتطوير؛ ليس زرًا داخل التطبيق. بعد الاختبار، لإعادة المحاكي إلى حالته العادية استخدم **Device Manager → ⋮ → Wipe Data** أو احذف المحاكي وأنشئ واحدًا جديدًا. في جهاز عادي غير مُهيّأ كـ Device Owner، يجب أن يرفض أندرويد منع الإزالة، ولا يمكن للتطبيق تجاوز هذا القيد بأمان.

### كيف أوقفه؟ وما الاحتياطات؟

- من داخل التطبيق، افتح الإعدادات وأطفئ مفتاح Kiosk؛ سيطلب التطبيق التأكيد بالرمز الرئيسي، ثم يطلب من أندرويد إيقاف Lock Task Mode وإزالة الحاسبة من قائمة السماح.
- اختبره أولًا على **جهاز احتياطي** مجهز لهذا الغرض، وليس هاتفك الأساسي. إعداد المشروع الحالي قد يعطّل عناصر من واجهة النظام، بما فيها قائمة إجراءات الطاقة وشاشة القفل وبعض طرق التنقل، ما دام Lock Task فعالًا. حضّر خطة استرداد من مسؤول الجهاز قبل التجربة.
- تأكد من أن بإمكانك العودة إلى إعدادات التطبيق وإيقاف المفتاح قبل استخدامه على جهاز يعتمد عليه يوميًا. لا تفترض أن رمز PIN داخل الحاسبة هو رمز خروج عام من Android Kiosk.
- لا يفعّل الكود الحالي إعدادًا دائمًا يجعل الحاسبة مشغّل Home الافتراضي، ولا يضيف تطبيقات أخرى إلى قائمة السماح، ولا يثبت صفة Device Owner بنفسه. كما أن معالج الإقلاع الموجود في المشروع يتعامل مع تذكير Extended Lock، وليس تشغيل Kiosk تلقائيًا بعد كل إعادة تشغيل.

### الفرق بين Kiosk وقفل التطبيقات ومنع الإزالة

| الميزة | ماذا تستهدف؟ | المتطلبات الأساسية في هذا المشروع |
|---|---|---|
| **App Lock** | يعرض بوابة PIN عند فتح التطبيقات التي تختار قفلها | تفعيل App Lock ومنح خدمة Accessibility صلاحيتها من إعدادات Android |
| **Kiosk** | يطلب من أندرويد تقييد الجهاز في وضع Lock Task للتطبيق المسموح | Device Owner وإعداد جهاز يدعم Lock Task Mode |
| **منع الإزالة** | يطلب منع إلغاء تثبيت تطبيق الحاسبة نفسه | Device Owner؛ مسؤول الجهاز العادي لا يضمن منع الإزالة |

هذه الميزات لا تتبادل الصلاحيات: تشغيل App Lock لا يشغّل Kiosk، وتفعيل Device Admin لا يضمن منع الإزالة، وظهور مفتاح Kiosk لا يثبت نجاح تفعيله.

## القيود الحقيقية في Android

- التطبيق لا يستبدل **Android Keyguard**.
- `BiometricPrompt` القياسي لا يكشف هوية الإصبع/البصمة المستخدمة.
- قفل شاشة الهاتف الفعلي يحتاج إلى تفعيل Device Admin ووجود PIN/نمط/كلمة مرور نظام مضبوطة؛ `lockNow()` قد يطفئ الشاشة فقط إذا لم يكن هناك نوع قفل نظام مضبوط. التطبيق لا يغيّر PIN نظام Android.
- PIN التطبيق لا يقرأ أو يغير PIN النظام.
- `5555` لا يمنع boot ولا يستبدل حماية Android عند الإقلاع.
- `7777` لا ينفذ Factory Reset.
- التشغيل من الخلفية والـoverlays وboot behavior تخضع لقيود Android وإصدار الجهاز.
- منع الإزالة بشكل قوي يعتمد على Device Owner؛ Device Admin العادي لا يجعل التطبيق غير قابل للإزالة مطلقًا.
- Accessibility App Lock يحتاج صلاحية يمنحها المستخدم.

## الاختبارات والتحقق

تشمل اختبارات المشروع regression والأمان، ومنها:

- Master PIN وDuress PIN.

- Emergency wipe ضمن نطاق بيانات التطبيق.
- Android Keystore وAES-GCM.
- Biometric bridge.
- Device Owner/Kiosk guards.
- Accessibility App Lock وحفظ المحاولات.
- fail-closed عند أخطاء التخزين.

- منع Factory Reset.
- ظهور الحاسبة أولًا وملء الشاشة.
- تمركز زر الصفر العريض.
- التسلسل السري الدقيق **`20272006=`** وفتح بوابة الحماية مباشرة.
- قبول **`0000`** تلقائيًا بعد الرقم الرابع والدخول إلى التطبيق المحمي.
- عدم وجود زر حماية مرئي أو مسار owner قديم.

عدد الاختبارات يتغير مع المشروع؛ المرجع النهائي هو نتيجة GitHub Actions للـcommit المطلوب اعتماده.

## تقرير التدقيق الشامل للإصدار — 16 أكتوبر 2026

راجِع [تقرير التدقيق التفصيلي](docs/SECURITY-AUDIT-2026-10-16.md) للاطلاع على الأخطاء المؤكدة، الأسباب الجذرية، الحلول المطبقة، المخاطر المتبقية، وخطة الاختبار.

### أهم نتائج التدقيق

1. **منع الإزالة:** ليس زرًا يمنح نفسه صلاحيات. الكود يستعمل `DevicePolicyManager.setUninstallBlocked`، وأندرويد يتطلب Device Owner للسماح بهذه السياسة. Device Admin العادي غير كافٍ، ولا توجد طريقة شرعية تجعل التطبيق مستحيل الإزالة على كل هاتف أو تمنع إعادة ضبط المصنع. أُضيف شرح السبب داخل الإعدادات، وتوثيق اختبار آمن على محاكي مُدار.
2. **قفل شاشة الهاتف:** أُضيف فحص `KeyguardManager.isDeviceSecure` ورسائل تشرح متطلبات النظام، وزر «اختبار قفل شاشة الهاتف الآن». إزالة إعدادات عرض النشاط فوق شاشة القفل تمنع واجهة التطبيق من إظهار نفسها فوق Keyguard الحقيقي. يجب ضبط قفل شاشة من إعدادات أندرويد.
3. **لوحة قفل التطبيقات:** استُبدل حقل إدخال النظام بلوحة أصلية تحتوي الأرقام والرموز والحذف والتأكيد والإرسال التلقائي، مع الاحتفاظ بعداد المحاولات والحظر. رموز المالك المهيأة تمر إلى منطق `submitPin` المركزي بدل نسخ سلوك مختلف داخل خدمة Accessibility.
4. **استرداد 5555:** كلمة «الصيانة» قابلة للنقر وتعرض عبارة استرداد واضحة؛ أدخل رمز المالك لإلغاء صيانة التطبيق. أُضيفت مهلة للمحاولات الخاطئة، ولا يعطّل الاسترداد سياسات Kiosk أو منع الإزالة تلقائيًا.
5. **أخطاء البناء في Windows:** أُصلح تشغيل Vite عبر ملفه JavaScript المحلي، وأُزيل تمرير مسار `node.exe` الموجود ضمن `Program Files` إلى shell، وهو ما تسبب برسالة `'C:\\Program' is not recognized`. جرّب الأمر `npm run apk:debug` بعد تحديث الملفات ونجاح التثبيت.

### الصلاحيات ليست قابلة للمنح الجماعي

أندرويد لا يسمح للتطبيق أن يمنح نفسه جميع الصلاحيات أو أن يحوّل نفسه إلى Device Owner بزر عادي. يجب أن يمنح المستخدم صلاحية Accessibility وOverlay وUsage Access وDevice Admin من شاشات النظام، بينما تعيين Device Owner يتم عبر مسار إعداد/Provisioning خاص بجهاز مُدار. لذلك يجب أن تعرض الواجهة الحالة الحقيقية بدل ادعاء أن كل الأذونات فعّالة.

### ملاحظات قبل اعتماد الإصدار

- القيم الافتراضية `0000/4444/5555/7777` مخصصة للاختبار ومعلومة لمن يقرأ المشروع؛ لا تستخدمها في نشر حقيقي دون تغييرها إلى رموز فريدة.
- فحص TypeScript والاختبارات والـlint لا يكفي وحده: يجب اكتمال بناء APK وفحوصاته ثم اختبار ميزات Device Admin وKeyguard وApp Lock على محاكي وجهاز أندرويد فعلي بإذن المالك.
- قفل التطبيقات يعتمد على أن خدمة Accessibility تبقى مفعّلة؛ المستخدم أو نظام Android يستطيع تعطيلها. Kiosk وDevice Owner مطلوبان لسيناريوهات إدارة الجهاز الأشد.
- بوابة قفل التطبيقات الأصلية تستخدم لوحة PIN والرموز والإجراءات الخاصة، لكن زر البصمة الاختياري الموجود في شاشة الدخول الرئيسية لم يُنقل بعد إلى Overlay الخاص بالتطبيقات الخارجية.
- تقرير التدقيق يميز بين **العيب المُصلح في الكود** و**القيد الذي يفرضه Android**، فلا يُعدّ الأخير خطأ يمكن إزالته برمجيًا.

## CI / GitHub Actions

مسار Android CI يتحقق من:

1. تثبيت dependencies.
2. اختبارات المشروع.
3. TypeScript.
4. إعداد Android وNative Kotlin.
5. بناء Debug APK.
6. فحص الـAPK والـmanifest النهائي.
7. التحقق من عدم وجود صلاحيات الشبكة غير المطلوبة.
8. رفع APK كـartifact عند نجاح البناء.

الإصدار القابل للتجربة يعتبر صالحًا فقط عندما تنجح جميع مراحل CI المطلوبة ويظهر artifact للـAPK.
