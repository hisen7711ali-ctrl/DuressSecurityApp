# الآلة الحاسبة — Duress Security App

تطبيق Android أمني وتجريبي محلي بواجهة **آلة حاسبة**، مع بوابة PIN، وApp Lock، وخزنة مشفّرة، وKiosk/Device Owner، وتكاملات Android أصلية للحماية والإدارة.

> **الفرع الحالي:** `merge/full-fix-2026-10-18`
>
> **حالة البناء الحالية:** تم بنجاح بناء Debug APK والتحقق منه عبر GitHub Actions. نجاح CI لا يعني أن جميع سياسات Android تعمل بالطريقة نفسها على كل جهاز؛ بعض الميزات تعتمد على إصدار Android والشركة المصنّعة وعلى تفعيل Device Admin/Device Owner أو الصلاحيات المناسبة.

## أبرز ما هو موجود حاليًا

- آلة حاسبة محلية حقيقية بدون استخدام `eval`.
- دعم الأصفار المتكررة في الإدخال ورموز الحاسبة.
- PINs قابلة للتغيير مع منع التعارض بين الرموز، ومنع حالات يكون فيها PIN قصير بادئةً لـPIN آخر.
- Master PIN، وDuress، وExtended Lock، ومسار طوارئ مستقل.
- قفل رئيسي وقفل مستقل للتطبيقات المحمية (App Lock).
- واجهة App Lock مستقلة تعرض اسم التطبيق وأيقونته ولوحة PIN خاصة به.
- فتح App Lock بالبصمة عبر `BiometricPrompt` مع إعادة التحقق من سياسة التطبيق قبل السماح بالفتح.
- خلفية مستقلة للقفل الرئيسي وApp Lock، مع presets وgallery ومعاينة وzoom/pan وحفظ مستقل.
- سجل محاولات فاشلة مشفّر، مع lockout متدرّج واستمرارية بعد إعادة التشغيل.
- Android Keystore وSecure Storage وAES-GCM لحماية البيانات الحساسة.
- Vault مشفّر يستخدم Argon2id للبيانات الجديدة مع توافق قراءة/ترحيل الصيغ السابقة.
- `FLAG_SECURE` لحماية الأسطح الحساسة من التقاط الشاشة.
- R8/ProGuard في Release مع قواعد keep محدودة للمكونات الأصلية المطلوبة.
- Device Admin للقفل عند الطلب.
- Device Owner/Kiosk عند provisioning الصحيح.
- أساس Direct Boot باستخدام `LOCKED_BOOT_COMPLETED` وDevice Protected Storage لسياسة App Lock الدنيا، مع إبقاء الأسرار في Credential-Encrypted Storage.
- فحوص Runtime دفاعية لاكتشاف مؤشرات root/tampering وMagisk/KernelSU/Xposed/Frida وبصمة توقيع APK. هذه مؤشرات دفاعية وليست ضمانًا مطلقًا ضد التلاعب.
- مسار اختياري لـShizuku لتنفيذ `pm clear` عند توفره والصلاحية المناسبة، مع بدائل Android الرسمية عند عدم توفره.
- حماية تمنع تنفيذ مسح التطبيق الأمني نفسه عند استخدام مسار مسح التطبيق المستهدف.

## الرموز الافتراضية والسياق

| الرمز | الوظيفة |
|---|---|
| `0000` | Master PIN — الدخول العادي |
| `4444` | Duress — فتح مسار واجهة الحاسبة الوهمية من سياق القفل |
| `5555` | Extended Lock — تشغيل القفل الممتد |
| `7777` | مسار طوارئ لمسح بيانات التطبيق المستهدف وفق سياسة Android المتاحة |
| `8888` | مسار Factory Reset ذي المرحلتين عند تفعيل سياسة Factory Reset |

هذه قيم افتراضية للمشروع التجريبي. **يجب تغييرها قبل الاستخدام الفعلي** وعدم اعتبار القيم الافتراضية بيانات اعتماد آمنة.

## سلوك PIN والحماية

- الـMaster PIN يأخذ الأولوية ولا يسمح لرمز آخر بأن يحل محله.
- يتم تطبيع الأرقام العربية والفارسية إلى أرقام ASCII قبل المقارنة.
- يتم رفض PINs المتكررة أو المتعارضة، بما في ذلك حالات البادئة التي قد تسبب إرسالًا تلقائيًا مبكرًا.
- المحاولات الفاشلة تخضع لـlockout متدرج يصل إلى حد أقصى محدد، ويُحفظ سجل المحاولات الحساسة بصورة مشفّرة على Android.
- Extended Lock يستمر لفترة طويلة محددة في طبقة الحماية، ويمكن استعادته فقط من مسار المالك المناسب.

## App Lock ومسح التطبيق المستهدف

عند تفعيل App Lock، يمكن اختيار التطبيقات التي يجب حمايتها. التطبيق الأمني نفسه لا يُعامل كتطبيق مستهدف للمسح.

مسار `7777` للتطبيق المستهدف يستخدم طبقات حماية متعددة حسب إمكانيات الجهاز:

1. محاولة `pm clear` عبر Shizuku إذا كان متاحًا ومصرحًا به.
2. استخدام `DevicePolicyManager.clearApplicationUserData()` عندما تتوفر صلاحية Device Owner المناسبة.
3. في حال عدم توفر المسارات الأصلية، يتم الانتقال إلى شاشة معلومات التطبيق في Android بدل الادعاء بأن المسح تم بنجاح.

مسح بيانات التطبيق المستهدف لا يعني بالضرورة حذف كل محتوى موجود خارج مساحة بيانات التطبيق، مثل بعض بيانات التخزين الخارجي.

## Factory Reset وDevice Owner

`DevicePolicyManager.wipeData()` هو API رسمي من Android لإعادة ضبط الجهاز عندما يكون التطبيق مهيأً كـDevice Owner وتسمح سياسة الإدارة بذلك.

مسار `8888` مصمم على مرحلتين:

- الإدخال الأول يقوم بالتسليح ولا ينفذ المسح.
- الإدخال الثاني يواصل مسار Factory Reset فقط عندما تكون سياسة Factory Reset مفعّلة.
- عند توفر Device Owner يتم تفضيل المسار الأصلي الآمن عبر `wipeData()`.
- عند عدم توفر الشروط اللازمة، لا يتم تنفيذ حذف ملفات يدوي على أنه Factory Reset؛ يتم استخدام مسار Android الاحتياطي/الإعدادات المناسب.

**لا ينبغي اعتبار `8888` ضمانًا لإعادة ضبط الهاتف على كل جهاز؛ تنفيذ Factory Reset يعتمد على سياسات Android وDevice Owner.**

## Device Admin وKiosk

يمكن للتطبيق طلب Device Admin لاستخدام وظائف مثل قفل الشاشة عند الطلب. تفعيل Device Admin وحده لا يجعل التطبيق Device Owner.

ميزات Kiosk/Dedicated Device وDevice Owner تحتاج provisioning رسمي مناسب للجهاز. لذلك قد تظهر الميزة غير مفعلة حتى بعد تثبيت APK عادي.

## Direct Boot

يدعم المشروع أساسًا لتطبيق App Lock بعد الإقلاع قبل فتح المستخدم للجهاز عبر:

- `LOCKED_BOOT_COMPLETED`.
- Device Protected Storage للحد الأدنى من سياسة القفل.
- إبقاء كلمات المرور والمفاتيح والبيانات الحساسة في Credential-Encrypted Storage.

بعد فتح الجهاز يعود التطبيق إلى التخزين المعتاد الآمن.

## التخزين والخزنة

- Secure Storage يعتمد على Android Keystore.
- البيانات الحساسة تستخدم تشفيرًا authenticated encryption.
- Vault يستخدم Argon2id للبيانات الجديدة مع دعم ترحيل الصيغ القديمة.
- ملفات الخزنة محلية على الجهاز ولا يعتمد التصميم على رفعها إلى خادم خارجي.

## Runtime Integrity

تشمل الفحوص الدفاعية الحالية مؤشرات مثل:

- حزم ومسارات معروفة لـMagisk وKernelSU وXposed/LSPosed.
- مؤشرات `su` وبعض مسارات root.
- مؤشرات Frida في خرائط العملية وبعض أسماء العمليات/المكتبات.
- بصمة SHA-256 لشهادة توقيع APK.
- installer package وحالة `debuggable`.

هذه الفحوصات يمكن أن تعطي false positives أو تفشل أمام تقنيات إخفاء متقدمة، لذلك لا يجب استخدامها وحدها لاتخاذ قرار أمني تدميري.

## البناء والتحقق عبر GitHub Actions

الفرع الحالي مجهز ببناء آلي لـDebug APK عبر GitHub Actions. مسار CI يقوم حاليًا بـ:

1. تثبيت Node وJava وAndroid SDK.
2. تحديث إصلاحات dependency الآمنة بدون ترقيات major قسرية.
3. تثبيت dependencies من lockfile.
4. إنشاء تقرير `npm audit` ورفض High/Critical غير المعالجة.
5. تشغيل الاختبارات.
6. فحص TypeScript.
7. فحص invariants الخاصة بالمصادقة والحماية.
8. تشغيل lint.
9. بناء Debug APK.
10. فحص APK النهائي للتأكد من بنيته وصلاحياته والمكونات الأساسية وعدم اعتماده على اتصال شبكي لإكمال البناء.
11. رفع APK كـArtifact باسم `duress-security-debug-apk`.

آخر تشغيل ناجح يجب اعتباره **إثباتًا لنجاح البناء والفحوص الآلية، وليس بديلًا عن اختبار APK على جهاز Android حقيقي**.

## الاختبار على جهاز حقيقي

يجب اختبار السلوك الفعلي على جهاز Android حقيقي، وخصوصًا:

- تغيير PINs والأرقام المتكررة مثل `00000000`.
- Master/Duress/Extended Lock ومسارات `7777` و`8888`.
- App Lock والتنقل بين التطبيقات المحمية.
- فتح App Lock بالبصمة.
- تغيير خلفيات القفل الرئيسي وApp Lock وحفظها بعد إعادة التشغيل.
- Device Admin وDevice Owner/Kiosk عند توفر provisioning.
- Direct Boot بعد إعادة التشغيل وقبل فتح الجهاز.
- Vault والتشفير والترحيل.
- الأذونات: Overlay وUsage Access وAccessibility والإشعارات وغيرها حسب إصدار Android.
- سلوك الجهاز بعد فشل الصلاحيات أو عدم توفر Shizuku/Device Owner.

اختلافات الشركات المصنّعة وإصدارات Android قد تؤثر في Accessibility وAutostart وKiosk وDevice Owner وإدارة الخلفية.

## ملاحظات مهمة

هذا المشروع **تجريبي/أمني محلي** وليس بديلًا عن نظام إدارة أجهزة مؤسسي أو ضمان أمني مطلق. يجب اختبار كل سياسة حساسة على الجهاز المستهدف قبل الاعتماد عليها.

لا يحتوي نجاح GitHub Actions وحده على إثبات أن جميع سياسات Android ستعمل على كل طراز هاتف.
