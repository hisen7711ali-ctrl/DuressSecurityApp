# الآلة الحاسبة — Duress Security App

تطبيق Android أمني وتجريبي محلي بواجهة **الآلة الحاسبة**، وبوابة PIN، وApp Lock، وVault مشفّر، وKiosk/Device Owner وتكاملات Android الأصلية.

> **الحالة:** المشروع قيد التطوير والتحقق عبر GitHub Actions. نجاح البناء لا يعني أن كل سياسات Android متاحة على كل جهاز؛ Device Owner يحتاج provisioning رسمي.

## ما تم بناؤه حتى الآن

- آلة حاسبة محلية حقيقية بدون `eval`، مع الحفاظ على الأصفار المتكررة في رموز الحاسبة.
- رمز حاسبة قابل للتغيير من الإعدادات، بطول 8 أرقام.
- `0000` Master PIN للدخول العادي، و`4444` لمسار الحاسبة/الـDuress من سياق القفل، و`5555` للقفل الممتد، و`7777` لمسار طوارئ مخصص لبيانات التطبيق المملوكة له.
- خلفية مستقلة للقفل الرئيسي وApp Lock، مع presets وgallery ومعاينة وzoom/pan وحفظ مستقل.
- App Lock بواجهة مستقلة تعرض اسم التطبيق وأيقونته ولوحة PIN مستقلة.
- BiometricPrompt بدون محاولة تحديد أي إصبع استُخدم.
- سجل محاولات فاشلة مشفّر مع حدود محاولات ومدة انتظار واستمرارية بعد إعادة التشغيل.
- Android Keystore وSecure Storage وAES-GCM.
- Vault يستخدم Argon2id للبيانات الجديدة مع توافق قراءة/ترحيل الصيغ القديمة.
- `FLAG_SECURE` لحماية الأسطح الحساسة من التقاط الشاشة.
- R8/ProGuard للـRelease مع قواعد keep محدودة للمكونات الأصلية المطلوبة.
- Device Admin وDevice Owner/Kiosk عند provisioning الصحيح.
- فحوص Runtime دفاعية لإشارات root/tampering وMagisk/KernelSU/Xposed/Frida وبصمة توقيع APK؛ هذه إشارات كشف وليست ضمانًا مطلقًا ضد التلاعب.
- أساس Direct Boot: مكوّنات `LOCKED_BOOT_COMPLETED` وDevice Protected Storage لسياسة App Lock الدنيا، مع إبقاء الأسرار الخاصة في Credential-Encrypted Storage.

## الرموز والسياق

| الرمز | الوظيفة |
|---|---|
| `0000` | Master PIN — الدخول العادي |
| `4444` | Duress / فتح واجهة الحاسبة الوهمية من سياق القفل |
| `5555` | Extended Lock / وضع الصيانة والقفل الممتد |
| `7777` | مسار طوارئ لبيانات التطبيق/التطبيق المستهدف عندما تكون سياسة Android المناسبة مفعلة |
| `8888` | محجوز لمسار Factory Reset ذي المرحلتين؛ لا يُعتبر تنفيذ المسح الكامل جاهزًا حتى يكتمل مسار Android الآمن |

هذه القيم افتراضية للمشروع ويجب تغييرها قبل الاستخدام الفعلي، باستثناء الرموز التي يفرضها التصميم الحالي حتى يتم استبدالها من إعداداتها.

## Factory Reset وDevice Owner

Android يميّز بين Device Admin وDevice Owner. `DevicePolicyManager.wipeData()` هو API رسمي لإعادة ضبط الجهاز إلى حالة المصنع عندما تكون سياسة الإدارة المناسبة متاحة، لكنه ليس عملية حذف ملفات عادية داخل WebView.

تصميم `8888` المطلوب للمشروع هو **تسليح ثم تأكيد**: الإدخال الأول لا ينفذ المسح، ويُعامل بصريًا كإدخال غير صالح؛ الإدخال الثاني من المالك يواصل مسار المسح. لا يجب أن يُنفذ المسح إلا من طبقة Android أصلية تتحقق من Device Owner وتستدعي API النظام، وليس عبر حذف ملفات أو قواعد بيانات يدويًا.

في النسخة الحالية تم تجهيز البنية الأمنية حول Device Owner وDirect Boot، لكن **Factory Reset الفعلي عبر `wipeData()` ما زال غير موصول**؛ لذلك لا يوجد ادعاء بأن `8888` يقوم بمسح الهاتف الآن.

## مسح بيانات تطبيق محمي

`DevicePolicyManager.clearApplicationUserData()` مختلف عن Factory Reset: فهو لمسح بيانات المستخدم لحزمة تطبيق محددة عندما يسمح Android بذلك للـDevice Owner/Profile Owner. ولا يعني ذلك بالضرورة حذف كل محتوى قد يكون خارج مساحة بيانات التطبيق، مثل بعض بيانات التخزين الخارجي.

لذلك يجب أن يبقى `7777` الخاص بالتطبيق المستهدف منفصلًا عن `7777` في قفل التطبيق نفسه، ومشروطًا بـDevice Owner وسياسة مالك صريحة لكل package.

## Direct Boot

يستخدم المشروع الآن Receiver متوافقًا مع `LOCKED_BOOT_COMPLETED` وتخزينًا محميًا بالجهاز لسياسة App Lock الدنيا. لا يتم نقل كلمات المرور أو مفاتيح الخزنة إلى Device Protected Storage؛ هذه تبقى في التخزين المشفر ببيانات الاعتماد. بعد فتح الجهاز يمكن العودة إلى التخزين المعتاد.

## Runtime Integrity

فحوصات Android الأصلية تسجل إشارات مثل:

- حزم Magisk وKernelSU وLSPosed/Xposed المعروفة.
- مسارات `su` وبعض مؤشرات Magisk/KernelSU.
- مؤشرات Frida في خرائط العملية وبعض أسماء العمليات/المكتبات.
- بصمة SHA-256 لشهادة توقيع APK وقت التشغيل.
- installer package وdebuggable state.

هذه الفحوصات دفاعية ويمكن أن تعطي false positives أو تفشل أمام أدوات إخفاء متقدمة؛ لذلك لا ينبغي استخدامها وحدها لاتخاذ قرار أمني تدميري.

## التحقق

يجب اعتبار APK صالحًا للتجربة بعد نجاح GitHub Actions في الاختبارات وTypeScript وlint وبناء Android. اختبار الخلفيات على أحجام شاشة متعددة، والرموز `4444/5555/7777` في الحاسبة والقفل الرئيسي وApp Lock، وDirect Boot، وKiosk، وVault، والصلاحيات، يحتاج أيضًا إلى جهاز Android حقيقي؛ CI لا يستطيع إثبات سلوك واجهة النظام على كل شركة مصنّعة.
