# Duress Security App

تطبيق Android أمني وتجريبي بواجهة **آلة حاسبة محلية**، وبوابة حماية PIN، وتخزين آمن، وApp Lock وتكاملات Android الأصلية.

> **الحالة:** المشروع قيد التطوير والتحقق عبر GitHub Actions. لا يُعتبر أي APK نهائيًا إلا بعد نجاح الاختبارات، TypeScript، بناء Android وفحوصات الـAPK النهائية.

## الواجهة والدخول المخفي

عند فتح التطبيق تظهر الآلة الحاسبة كواجهة أولى عادية وملء الشاشة، بدون زر حماية ظاهر.

### رمز الدخول المخفي

التسلسل الحالي والدقيق هو:

**`2 → 0 → 2 → 7 → 2 → 0 → 0 → 6 → =`**

أي أن الرمز الكامل هو:

**`20272006=`**

بعد الضغط على `=` بعد الرقم الثامن، يجب أن تنتقل الحاسبة مباشرة إلى **بوابة الحماية PIN**. لا يوجد ضغط متكرر على `=`، ولا زر وسيط، ولا اعتماد على الإنترنت.

الحاسبة نفسها حقيقية ولا تستخدم JavaScript `eval` لتنفيذ العمليات.

## PIN والحماية

| PIN | الوظيفة |
|---|---|
| `0000` | Master PIN — الدخول العادي إلى مساحة الحماية |
| `4444` | Duress / Fake Calculator Mode |
| `5555` | Extended Lock لمدة 30 يومًا |
| `7777` | Emergency wipe لبيانات التطبيق المملوكة له فقط |
| PIN آخر | رفض المحاولة مع حماية من المحاولات المتكررة |

عند إدخال **`0000`** في بوابة الحماية، يتم قبول الـPIN تلقائيًا بعد الرقم الرابع والدخول إلى التطبيق المحمي، بدون زر تأكيد إضافي.

هذه القيم افتراضية/اختبارية للمشروع وليست بديلًا عن PIN نظام Android.

### Emergency `7777`

المسح الطارئ محصور في بيانات التطبيق التي يملكها التطبيق. لا ينفذ Android Factory Reset ولا يمسح بيانات الهاتف الشخصية.

### Extended Lock `5555`

يحفظ التطبيق حالة القفل ومدة الثلاثين يومًا ضمن التخزين الأمني ويحاول استعادتها بعد إعادة التشغيل ضمن قيود Android.

## Offline / Local App

التطبيق مصمم ليعمل **بدون اتصال إنترنت أثناء التشغيل**.

- واجهة التطبيق وملفات WebView مضمّنة محليًا داخل الـAPK.
- لا يعتمد التطبيق على موقع ويب أو خادم خارجي لعرض الشاشة الرئيسية.
- إعداد Capacitor يستخدم `dist/client` كـ`webDir` محلي.
- لا توجد سماحية تشغيلية لـ`INTERNET` أو `ACCESS_NETWORK_STATE` في الـmanifest النهائي.
- GitHub Actions وبيئة التطوير تحتاجان الإنترنت فقط أثناء البناء وتنزيل dependencies وAndroid SDK/Gradle.

> ملاحظة: الواجهة مبنية بتقنيات Web UI لكنها **معبأة محليًا داخل تطبيق Android** وليست موقعًا خارجيًا يتم تحميله من الإنترنت.

## الأيقونة والهوية البصرية

- أيقونة launcher مرتبطة بتصميم آلة حاسبة.
- `android:icon` و`android:roundIcon` يستخدمان مصدر الأيقونة النهائي.
- `android-setup.mjs` يجهز موارد Android النهائية أثناء البناء.
- اسم التطبيق الظاهر: **الآلة الحاسبة**.
- Package: `com.duresssecurity.app`.

## حماية جلسة التطبيق

- عند فتح بوابة الحماية من الحاسبة يتم تعطيل استعادة الحاسبة أثناء انتقال الدخول.
- بعد نجاح Master PIN لا يفترض أن تعيد أحداث visibility/background المؤقتة المستخدم مباشرة إلى الحاسبة.
- جلسة التطبيق تُقفل عند الانتقال للخلفية وفق سياسة الحماية.
- `MainActivity.onStop()` يرسل إشارة native إضافية لإعادة القفل عند الحاجة.
- أخطاء التخزين الأمني في مسارات الحماية تعمل بأسلوب **fail-closed**.

## App Lock

عند منح Accessibility permission يمكن استخدام App Lock للتطبيقات المحددة في السياسة.

- بوابة PIN قبل الوصول إلى التطبيقات المحمية.
- عداد محاولات محفوظ لكل package.
- إعادة عرض البوابة لا تصفر العداد.
- الحظر المؤقت محفوظ مع عدد المحاولات.
- فشل قراءة أو فك تشفير حالة المحاولات لا يتحول إلى fail-open.

## التخزين والتشفير

- Android Keystore لإدارة مفاتيح التشفير.
- AES-GCM للبيانات الحساسة.
- Secure Storage أصلي.
- حماية vault من العبث.
- retry lockout محفوظ.
- PBKDF2 + AES-GCM للـvault بدون plaintext fallback.
- emergency reset محصور ببيانات التطبيق.

## Android Native

يتضمن المشروع:

- `DevicePolicyManager.lockNow()` عبر Device Admin عند توفر الصلاحية.
- `BiometricPrompt`.
- Android Keystore Secure Storage.
- Permission status/request handling.
- Accessibility App Lock.
- Device Owner / Kiosk عند provisioning الرسمي.
- Boot/restart handling ضمن قيود Android الحديثة.

### Android build

- `MainActivity.kt` يتم تضمينه صراحة في Android app module.
- Native security classes يتم نسخها إلى مشروع Android أثناء الإعداد.
- Java/Kotlin موحدان على **JVM 21**.
- يستخدم المشروع Kotlin Android plugin.
- compile/target SDK: **35**.
- يتم فحص الـmanifest النهائي للتأكد من عدم وجود صلاحيات الشبكة غير المطلوبة.

## وضع Kiosk (تقييد الجهاز) — دليل الاستخدام الفعلي

### ما هو Kiosk في هذا المشروع؟

**Kiosk ليس رمز PIN ولا ميزة قفل تطبيق واحد.** هو محاولة تشغيل الحاسبة في وضع أندرويد المسمّى **Lock Task Mode**، والمخصص للأجهزة التي يُراد أن تبقى ضمن تطبيق واحد أو مجموعة تطبيقات معتمدة. يناسب مثلًا جهازًا مخصصًا لعرض الحاسبة فقط أو جهازًا مخصصًا لمهمة محددة.

### ماذا ينفّذ الكود الموجود حاليًا؟

عند تشغيل المفتاح من إعدادات التطبيق، يحاول الجسر الأصلي تنفيذ هذه الخطوات:

1. يتحقق أولًا من أن تطبيق الحاسبة مسجّل لدى أندرويد بصفته **Device Owner**.
2. يضيف حزمة تطبيق الحاسبة وحدها إلى قائمة التطبيقات المسموح لها بالبقاء في Lock Task Mode.
3. على Android 9/API 28 وما بعده، يضبط ميزات واجهة وضع التقييد باستخدام `LOCK_TASK_FEATURE_HOME`.
4. يطلب من النشاط الحالي بدء Lock Task Mode.
5. عند إيقاف المفتاح، يطلب إيقاف Lock Task Mode وإزالة الحاسبة من القائمة المسموح بها.

إذا رفض أندرويد الخطوة المطلوبة، يعيد الجسر نتيجة فشل ويعرض التطبيق رسالة تفيد بأن أندرويد لم يسمح بتفعيل الوضع. لذلك **ظهور المفتاح في الواجهة لا يعني أن Kiosk قد أصبح فعالًا**؛ يجب التحقق من حالة الجهاز ورسالة النتيجة.

### ما الذي يمكن أن يقيّده عند نجاح التفعيل؟

على جهاز أُعدّ رسميًا كجهاز مُدار، ومع إصدار أندرويد يدعم Lock Task Mode، يمكن لهذا الوضع أن يقيّد الانتقال إلى التطبيقات غير المدرجة في قائمة السماح، ويحدّ من عناصر واجهة النظام مثل لوحة الإشعارات وشاشة التطبيقات الأخيرة. في هذا المشروع، القائمة التي يضبطها الكود تحتوي على تطبيق الحاسبة وحده.

**تفصيل مهم عن زر الشاشة الرئيسية:** الكود الحالي يفعّل ميزة `LOCK_TASK_FEATURE_HOME` في Android 9 وما بعده. وفق سلوك أندرويد الموثّق، قد يظهر زر Home، لكن الضغط عليه لا يفتح المشغّل الافتراضي عادةً ما دام ذلك المشغّل غير مُضاف إلى قائمة السماح. لا يضيف الكود الحالي المشغّل الافتراضي ولا يعيّن الحاسبة تطبيق Home افتراضيًا. أما الإصدارات الأقدم من Android 9 فلا يضبط الكود لها هذه المجموعة من ميزات الواجهة، وقد يختلف السلوك حسب إصدار النظام والشركة المصنّعة.

### كيف أفعّله من داخل التطبيق؟

1. استخدم **نسخة Android المثبّتة** من التطبيق؛ المعاينة في المتصفح لا تستطيع تفعيل سياسات الجهاز الأصلية.
2. افتح الحاسبة، ادخل بالطريقة المعتادة إلى مساحة الحماية، ثم افتح **الإعدادات**.
3. قبل تشغيل Kiosk، يجب أن يكون الجهاز قد أُعدّ مسبقًا بحيث يكون التطبيق **Device Owner**. لا يستطيع التطبيق منح نفسه هذه الصفة من داخل الإعدادات.
4. شغّل مفتاح **وضع الجهاز المخصّص (Kiosk)**. سيطلب التطبيق تأكيد العملية بالرمز الرئيسي وفق نافذة التأكيد الموجودة فيه.
5. راقب النتيجة: حالة إدارة الجهاز توضّح ما إذا كانت صفة Device Owner متاحة، وحالة Kiosk الفعلية تُقرأ من حالة Lock Task التي يبلغ عنها أندرويد. إذا ظهرت رسالة أن أندرويد لم يسمح بالتفعيل، فالوضع لم يُفعّل بنجاح.

### ما الفرق بين Device Admin وDevice Owner؟

هما صلاحيتان مختلفتان وليستا اسمين للشيء نفسه:

- **Device Admin (مسؤول الجهاز):** زر التفعيل الموجود في إعدادات التطبيق يطلب من أندرويد صلاحية الإدارة التقليدية. يستخدم المشروع هذه الصلاحية، عند توفرها، لطلب قفل الشاشة عبر `DevicePolicyManager.lockNow()`.
- **Device Owner (مالك الجهاز):** وضع إدارة أعلى يحتاج إلى إعداد رسمي للجهاز المُدار. يعتمد الكود عليه لتطبيق سياسة منع إزالة التطبيق وللسماح بتفعيل Kiosk. مجرد الموافقة على نافذة Device Admin لا تجعل التطبيق Device Owner ولا تكفي وحدها لتشغيل Kiosk.

تعيين Device Owner يتم عبر مسار إعداد/Provisioning مخصص لأجهزة أندرويد المُدارة، وليس بزر داخل التطبيق. قد يتطلب تجهيز الجهاز من البداية وفق تعليمات أندرويد أو مسؤول المؤسسة؛ لا تفترض أن هاتفًا شخصيًا مُعدًّا مسبقًا يمكن تحويله إلى هذه الحالة دون إعادة تهيئة أو شروط إضافية. راجع [دليل Android الرسمي لوضع Lock Task](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode) و[إرشادات الأجهزة المخصصة](https://developer.android.com/work/dpc/dedicated-devices).

### كيف أوقفه؟ وما الاحتياطات؟

- من داخل التطبيق، افتح الإعدادات وأطفئ مفتاح Kiosk؛ سيطلب التطبيق التأكيد بالرمز الرئيسي، ثم يطلب من أندرويد إيقاف Lock Task Mode وإزالة الحاسبة من قائمة السماح.
- اختبره أولًا على **جهاز احتياطي** مجهز لهذا الغرض، وليس هاتفك الأساسي. الوضع مصمم لتقييد التنقل وقد يجعل الوصول إلى أجزاء من واجهة النظام أصعب ما دام فعالًا.
- تأكد من أن بإمكانك العودة إلى إعدادات التطبيق وإيقاف المفتاح قبل استخدامه على جهاز يعتمد عليه يوميًا. لا تفترض أن رمز PIN داخل الحاسبة هو رمز خروج عام من Android Kiosk.
- لا يفعّل الكود الحالي إعدادًا دائمًا يجعل الحاسبة مشغّل Home الافتراضي، ولا يضيف تطبيقات أخرى إلى قائمة السماح، ولا يثبت صفة Device Owner بنفسه. كما أن معالج الإقلاع الموجود في المشروع يتعامل مع تذكير Extended Lock، وليس تشغيل Kiosk تلقائيًا بعد كل إعادة تشغيل.

### الفرق بين Kiosk وقفل التطبيقات ومنع الإزالة

| الميزة | ماذا تستهدف؟ | المتطلبات الأساسية في هذا المشروع |
|---|---|---|
| **App Lock** | يعرض بوابة PIN عند فتح التطبيقات التي تختار قفلها | تفعيل App Lock ومنح خدمة Accessibility صلاحيتها من إعدادات Android |
| **Kiosk** | يطلب من أندرويد تقييد الجهاز في وضع Lock Task للتطبيق المسموح | Device Owner وإعداد جهاز يدعم Lock Task Mode |
| **منع الإزالة** | يطلب منع إلغاء تثبيت تطبيق الحاسبة نفسه | Device Owner؛ مسؤول الجهاز العادي لا يضمن منع الإزالة |

هذه الميزات لا تتبادل الصلاحيات: تشغيل App Lock لا يشغّل Kiosk، وتفعيل Device Admin لا يضمن منع الإزالة، وظهور مفتاح Kiosk لا يثبت نجاح تفعيله.

## القيود الحقيقية في Android

- التطبيق لا يستبدل **Android Keyguard**.
- `BiometricPrompt` القياسي لا يكشف هوية الإصبع/البصمة المستخدمة.
- PIN التطبيق لا يقرأ أو يغير PIN النظام.
- `5555` لا يمنع boot ولا يستبدل حماية Android عند الإقلاع.
- `7777` لا ينفذ Factory Reset.
- التشغيل من الخلفية والـoverlays وboot behavior تخضع لقيود Android وإصدار الجهاز.
- منع الإزالة بشكل قوي يعتمد على Device Owner؛ Device Admin العادي لا يجعل التطبيق غير قابل للإزالة مطلقًا.
- Accessibility App Lock يحتاج صلاحية يمنحها المستخدم.

## الاختبارات والتحقق

تشمل اختبارات المشروع regression والأمان، ومنها:

- Master PIN وDuress PIN.
- Extended Lock وحفظ/انتهاء الحالة.
- Emergency wipe ضمن نطاق بيانات التطبيق.
- Android Keystore وAES-GCM.
- Biometric bridge.
- Device Owner/Kiosk guards.
- Accessibility App Lock وحفظ المحاولات.
- fail-closed عند أخطاء التخزين.
- vault tamper detection.
- منع Factory Reset.
- ظهور الحاسبة أولًا وملء الشاشة.
- تمركز زر الصفر العريض.
- التسلسل السري الدقيق **`20272006=`** وفتح بوابة الحماية مباشرة.
- قبول **`0000`** تلقائيًا بعد الرقم الرابع والدخول إلى التطبيق المحمي.
- عدم وجود زر حماية مرئي أو مسار owner قديم.
- وجود `MainActivity.kt` وNative Kotlin classes.
- اتساق JVM 21.
- فحوصات network guard والـoffline manifest.
- فحص أيقونة launcher المرتبطة بتصميم آلة حاسبة فعلي.

عدد الاختبارات يتغير مع المشروع؛ المرجع النهائي هو نتيجة GitHub Actions للـcommit المطلوب اعتماده.

مسار Android CI يتحقق من:

1. تثبيت dependencies.
2. اختبارات المشروع.
3. TypeScript.

## ملاحظات الاستخدام
